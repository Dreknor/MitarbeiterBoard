# AGENTS.md – MitarbeiterBoard

## Overview

Laravel 12 school intranet ("MitarbeiterBoard") for the Evangelisches Schulzentrum Radebeul. German-language domain (models, views, config). PHP 8.2+, MySQL/MariaDB, Vite + TailwindCSS v4, Alpine.js, Livewire 4, Bootstrap 4 (legacy).

## Architecture

- **Monolith** – single Laravel app, server-rendered Blade views, no SPA. Alpine.js handles interactive UI (diagnostics, wochenplan, sidebar).
- **Laravel 12 with the Laravel 10 app skeleton** – `app/Http/Kernel.php`, `app/Console/Kernel.php`, `app/Exceptions/Handler.php`, `config/app.php` providers/aliases and `RouteServiceProvider` are kept on purpose (still supported); no `bootstrap/app.php` fluent config. Carbon 3: `diffIn*()` returns a signed float – write `(int) $a->diffInDays($b, true)` where the old absolute integer is meant. `composer.json` uses `minimum-stability: stable` (no dev versions in the lock). Key majors: Sanctum 4, spatie/laravel-permission 6 (config must keep `register_permission_check_method => true`), Media Library 11, laravel-dompdf 3 (`setOptions()` replaces all options unless the second argument is `true`), PHPUnit 11.
- **Dual CSS** – Legacy pages use Bootstrap 4 (`public/css/`). Newer modules (diagnostics, paedDiary, wochenplan, rooms, sidebar) use Tailwind v4 via Vite. Tailwind preflight is **disabled** (`corePlugins.preflight: false`) to avoid Bootstrap conflicts. Tailwind is scoped via wrapper classes (e.g. `.diagnostic-wrapper`).
- **Vite entrypoints** are per-module, not a single bundle – see `vite.config.js`. Views load assets with `@vite()` and `@push('css')`/`@push('js')`.
- **Authorization** uses `spatie/laravel-permission` (RBAC). Permissions are checked via route middleware (`permission:view wiki`) and in controllers. Policies exist for `DiagnosticSession`, `DiagnosticArea`, `WpPlan` (`WpPlanPolicy`), `GradingDocumentationSession`, `Meeting`, `Post` (`PostPolicy`), `WikiSeite` (`WikiSeitePolicy`), Procedures, Personal and (API v1) `Schueler` (`StudentPolicy`) and `PaedDiaryEntry` (`PaedDiaryPolicy`).
- **SSO** via SAML2 (`aacotroneo/laravel-saml2`) and Keycloak (`socialiteproviders/keycloak`). Local auth can be toggled via `AUTH_LOCAL` env.
- **Meetings** can be group-bound (`group_id`) or free (`group_id = null`). Participants live in `meeting_participants` (polymorphic: `User` incl. `is_organizer`, `Group`, Spatie `Role`); visibility via `Meeting::scopeVisibleTo()` and `MeetingPolicy` (`view`/`contribute`/`manage`/`viewTheme`). Group-independent UI under `/meetings` (`app/Http/Controllers/Meetings/`), shared logic in `Services/Meetings/MeetingService`. Themes may be free (`themes.group_id = null`) and are then only reachable via `meetings/{meeting}/agenda/{theme}`. New agenda themes can be assigned to the meeting group or any invited group (`MeetingService::themeGroupOptions()`/`isValidThemeGroup()`), so unfinished themes stay in that group's list; free themes only in free meetings. Existing open agenda themes can be moved later via `meetings.themes.move` (`MeetingService::themeMoveTargets()`/`moveTheme()`; only themes whose current group belongs to the meeting). Global search: `Services/Search/GlobalSearchService` (includes themes/protocols of meetings the user participates in). Free meetings require the permission `create free meetings`. Invitations (`MeetingService::sendInvitations()`) can be limited to selected participants (`select_recipients` + `recipients[]`, validated in `validateInvitationRequest()`, UI `meetings/partials/invite_recipients.blade.php`); this only affects who gets the mail/push – access stays with all group members and invitees.
- **Theme tasks** (`Task`): personal (`taskable = User`) or collective (`taskable = Group|Meeting`, assignees in `group_task_users` with `completed_at` – rows are marked, never deleted, so "who completed" stays visible; unique per task+user). All creation/completion goes through `Services/Tasks/ThemeTaskService` (duplicate protection per person on same theme + same text). `Task` has a global scope hiding completed tasks – use `Task::withCompleted()` for history. Shared UI: `resources/views/tasks/partials/theme_tasks.blade.php` + `task_form.blade.php` (used by group and meeting theme pages).
- **Calendar (OX)**: OX (CalDAV) is the system of record; `ox_termine` is only a local cache filled by `OxCalendarService::syncAll()`. Every write goes to OX first. A termin can live in several calendars ("Terminverbund"): each copy is its own OX event (own UID), linked via `ox_termine.verbund_uid` and the iCal property `X-MB-VERBUND` (survives the OX roundtrip). Create/update/move/delete across copies only via `Services/Calendar/TerminVerbundService`; room bookings hang on the verbund (`room_bookings.ox_verbund_uid`) via `Services/Calendar/KalenderRaumService` (also renders room occupancy as FullCalendar events, incl. A/B weeks and VP cancellations). ICS import: `Services/Calendar/IcsImportService` + `CalendarImportController` (preview cached per user/token, permission `import calendar events`). OX rights of the service account: `ox_calendars.ox_schreibrecht` (null = unknown, never blocks) is set from CalDAV `current-user-privilege-set` (`bind`/`write`/`all`) by `OxCalendarService::oxRechtePruefen()` after every `syncAll()` and when a calendar is added, and set to false on HTTP 403 when creating; locked calendars are excluded by `canWriteCalendar()` but shown disabled with explanation (`gesperrtDurchOx()`, `OxCalendar::OX_SPERRE_HINWEIS`, partial `calendar/partials/gesperrteKalender`) in the termin form and ICS import (import stops after the first 403 per calendar and reports it once), plus a banner in the calendar admin. Calendar CSS loads Tailwind utilities **unlayered** and resets Bootstrap element styles inside `.calendar-wrapper` – see header comment in `resources/css/calendar.css`.
- **Nachrichten** (`Post`, `PostLesestatus`): one model for dashboard announcements and longer group messages (title, optional `kurzfassung`, TinyMCE `text`, media collections `images`/`files`). Targets are groups (`group_post`); `auf_dashboard` decides whether a post also shows on the dashboard card (`NachrichtenComposer` → `PostService::dashboardNachrichten()`, open own confirmations pinned on top). Every group has a page `{groupname}/nachrichten` (current/archive, sidebar entry with unread badge via `ungeleseneJeGruppe()`), and the theme pages show unread/unconfirmed posts via `posts/partials/gruppen_hinweis.blade.php`. All rules live in `Services/Posts/PostService`, access in `PostPolicy`: posting with `create posts` into own groups, group creators always into their group, `manage posts` into all groups (and edit/archive every post); `request read confirmation` (or `manage posts`) may request read confirmations. Published posts are never deleted, only archived (`archived`/`archiviert_at`, restorable by author/`manage posts`); only never-published drafts are soft-deleted; once published a post stays published. Optional `sichtbar_bis` auto-archives daily – posts with a running confirmation deadline only after it. Read confirmation = explicit click (`posts.confirm`), recipients are the **current** members of the target groups (`group_user`) except the author, deleted accounts excluded: new members get the confirmation assigned (hourly `abgleichen()` + directly in `GroupController::addUser`) with their own deadline (original duration from join, at least 7 days); members who left keep their confirmation in the list, open entries of leavers disappear. `post_lesestatus` stores per person `gelesen_at` (only for unread markers/counts, never shown to others; "unread" counts only the last `Post::NEU_TAGE` days), `bestaetigt_at`, `zugewiesen_at`, `frist` and reminder stamps. Editing a published post with confirmation asks whether to keep or reset confirmations (`bestaetigungen_zuruecksetzen`, default keep); requesting it later assigns it to everyone. Reminders: automatically 2 days before and on the deadline (daily `erinnerungenVersenden()`, none afterwards), manually at most once per day (`posts.remind`). The confirmation list (`posts.confirmations`, Excel `PostBestaetigungenExport`, PDF `pdf/post_bestaetigungen.blade.php` with `PdfLayout`) is visible to the author, `manage posts` and creators of a target group (view only). Notifications: `NachrichtVeroeffentlicht` (category `nachrichten`; without confirmation bell/push by preference, mail stays the 20:00 digest `PostsController::dailyMail`) and `NachrichtErinnerung`; anything with read confirmation always goes out immediately over all channels (`NachrichtKanaele::alle()`). Text is rendered only via `text_html` (`HtmlSanitizer`); attachments only via `posts.files` (`/image/{id}` redirects there after a policy check). UI: Tailwind via `resources/css/posts.css` + `resources/js/posts.js` (TinyMCE, Alpine `nachrFiles`), scoped `.nachr-wrapper`/`nachr-*`, utilities unlayered/`!important` like tickets; tour `<x-tour id="nachrichten">`. The dashboard quick form (JSON `POST posts`) stays for short posts. API: see Nachrichten API below. Tests: `tests/Feature/Posts/`.
- **Ticketsystem** (`Ticket`, `TicketComment`, `TicketCategory`): all creation, comments, status changes (open/waiting/closed, reopen), assignment, pins and notifications go through `Services/Tickets/TicketService`; access via `TicketPolicy` (`view`/`comment`/`manage`/`close`/`reopen`/`viewInternal` – creators see only their own tickets, `edit tickets` sees all and may comment internally). Mutating routes are POST. Rich-text (description/comments) is rendered only via `description_html`/`comment_html` (`App\Support\HtmlSanitizer`, HTMLPurifier). Attachments live on the private disk `tickets` and are served only via `tickets.files`. Waiting tickets are auto-closed daily (`closeExpiredWaiting`, settings `ticket_closed_automatic[_days]`). UI: Tailwind via `resources/css/tickets.css` + `resources/js/tickets.js`, scoped in `.ticket-wrapper` with `tkt-*` components; utilities are loaded **unlayered and `!important` with `source(none)`** (only ticket views are scanned) so they beat Bootstrap element styles – elements with display utilities need `x-show.important`. Below `lg`, list and detail are separate views.
- **Zeitwirtschaft** (Urlaub, Arbeitszeitnachweis, Dienstplan, Zeiterfassung): logic lives in `app/Services/Personal/Zeit/` – `ArbeitszeitService` (single source for Soll-Zeit/Arbeitstage from `Employment.percent` × Setting `vollzeit_stunden`, distributed over `employments.workdays`; public holidays computed locally in `App\Support\Feiertage`), `UrlaubskontoService` (Anspruch/Übertrag/Verfall/Rest, manual entries in `holiday_account_entries`), `HolidayService` (request/approve/reject/cancel + notifications), `TimesheetService` (Soll/Ist separation, balance cascade into following months, workflow offen → eingereicht → abgeschlossen), `RosterService` (create/copy weeks, absence markers `roster_events.source = 'abwesenheit'`, conflicts, publish + change log `roster_changes`, ICS feed), `TimeRecordingService` (Kommen/Gehen incl. § 4 ArbZG break). Access via `HolidayPolicy`/`TimesheetPolicy`/`RosterPolicy` and `ZeitZugriff` (superior chain incl. deputies from `user_deputies` – a deputy may do everything the represented leader may, if holding the permission; bulk maintenance under `personal/vorgesetzte`, `VorgesetzteController`; permissions `approve all holidays`, `manage all rosters`). Syncing is event driven: `HolidayObserver` and `AbsenceTimeObserver` keep absences (`absences.holiday_id`), timesheet credits (`timesheet_days.source` `urlaub`/`abwesenheit`, only on contract workdays) and roster markers consistent; `WorkingTimeObserver`/`RosterEventsObserver` log changes to published rosters. All mutating routes are POST/PUT/DELETE; `timesheets/{user}/{timesheet}` uses `scopeBindings()`. Terminal (`/time_recording`) keeps the scanned chip in the session only, PINs are hashed, throttled and lock after 5 failures; optional device binding via Setting `time_recording_terminal_token`. UI: Tailwind via `resources/css/zeit.css` + `resources/js/zeit.js` (Alpine `urlaubsAntrag`, `teamKalender`, `dienstplanEditor`), scoped in `.zeit-wrapper` with `zw-*` components, utilities unlayered/`!important` like tickets; roster editor loads its data via `roster.data` (JSON). Legacy protection: Setting `zeitwirtschaft_stichtag` – timesheets before it are calculated with the old method (`TimesheetService::berechneBisher()`), past ones are frozen (only recalculated on explicit edit/"Neu berechnen"); the old daily Soll uses the contracts valid on that day (`ArbeitszeitService::vertraegeAm()`), not their current status – expired contracts are set to `beendet` daily; the holiday balance continues from the stored `holidays_rest` of the month before the cutover (`UrlaubskontoService::basis()`). Check real data read-only with `php artisan personal:zeit-umstellung-pruefen`. Tests: `tests/Feature/Personal/Zeit/`.
- **Abwesenheiten** (`/absences`, `view absences` + `view old absences`): `AbsenceController` filters/paginates server-side (`zeitraum` aktuell|heute|geplant|vergangen|alle, `q`, `grund`, `person`, `von`/`bis`); the Excel export (`absences.export`, `AbsenceExport`) takes the same filters. Create/merge/delete only via `Services/AbsenceService` (merges only overlapping/adjacent entries of the same person + reason, never holiday absences; `loeschbarDurch()` = right + end after today + no `holiday_id`). Delete is `DELETE absences/{absence}` (no GET link). `Absence` keeps its `VertretungsplanAbsence` in sync in `saved`/`deleted` (linked via `absence_id`, legacy rows without it are matched by person + start); sick reasons from `config('absences.absence_sick_note')` longer than `Absence::krankenscheinTage()` set `sick_note_required`. UI: Tailwind via `resources/css/absences.css`, scoped `.abw-wrapper`/`abw-*`, utilities unlayered/`!important` like tickets, form partial `absences/partials/formular.blade.php`, tour `<x-tour id="abwesenheiten">`. **Wiederkehrende Abwesenheiten** (`AbsenceSerie`, table `absence_series`, `Services/AbsenceSerieService`): the rule (weekly on chosen weekdays every N weeks, or monthly on the 1st–4th/last weekday) is stored once, every occurrence becomes a normal one-day `Absence` with `serie_id` – so Vertretungsplan, timesheets, export and API work unchanged. Start ≥ today, max. one year, no sick reasons (`grundErlaubt()`); weekends/holidays and days the person is already absent (any reason) are skipped, series occurrences are never merged; one notification per series (`AbwesenheitsserieGemeldet`). `DELETE absences/serie/{serie}` deletes only future occurrences, the rule stays (no editing – delete and recreate). Form fields come from the shared partial `absences/partials/serie.blade.php` (Alpine, styling via `$serienKlassen`), used in `/absences` and both dashboard cards (the toggle is always visible – the default reason is usually „krank“, so switching it on clears a sick reason). API: `POST /api/v1/absences/series` (`frequency`, `weekdays`, `interval`, `month_position`, `month_weekday`; returns `created`/`skipped`/`absences`), `DELETE /api/v1/absences/series/{id}` (future occurrences), every absence carries `series`, `options.series` lists the allowed values (`AbsenceSeriesApiTest`). Tests: `tests/Feature/Absences/` (`WiederkehrendeAbwesenheitenTest`).
- **Krankmeldungen** (`/sick_notes`, `manage sick_notes`): `KrankmeldungController` + `Services/KrankmeldungService` (single source for all rules, used by page and Excel export `SickNotesCompleteExport` = list + persons + statistics sheet). Sick note needed **from the N-th sick day counted in working days** (default 3, `Absence::krankenscheinTage()`, setting `absence_sick_note_days`; due on that day; the model sets `sick_note_required` automatically) or it was explicitly requested (`sick_notes.pflicht`, then due from day 1); status `fehlt|ausstehend|liegt_vor|nicht_noetig`. Working days exclude weekends/holidays; statistics count only days inside the chosen period (`zeitraum` 12monate|schuljahr|jahr|vorjahr|frei). Kurzerkrankung/BEM only for own sickness (`config('absences.absence_own_sick')`, not "Kind krank"); BEM hint at ≥ 30 working days in the last 12 months. Changes only via POST/DELETE (`sick_notes.schein`, `sick_notes.schein.entfernen`). UI shares `resources/css/absences.css`; tour `<x-tour id="krankmeldungen">`. Tests: `tests/Feature/Absences/KrankmeldungenTest.php`.
- **Tagesinfos aus dem Vertretungsplan-Import** (`DailyNews`, `API\VertretungsplanImportController`): `InfoK` of the actions becomes a daily info only once per day and text (whitespace-normalised, `DailyNews::normalisieren()`/`schluessel()`), also against earlier imports and manually created infos. The plain token is shown once via session flash. Tests: `tests/Feature/API/v1/ApiTokenProfileTest.php`.
  - Diary content is encrypted at rest (`PaedDiaryEntry::setContentAttribute`), so full-text search cannot use SQL – `Api\PaedDiarySearchService` decrypts pre-filtered entries and matches in PHP (max. 5000 per search). App config: `config/paed_app.php`.

## Conventions

- **Language**: All UI text, model names, comments, and config keys are in **German** (e.g. `Schueler`, `Klasse`, `Vertretung`, `Wochenplan`, `Meldung`). Keep this convention.
- **Flash messages** use `session('Meldung')` with `session('type')` for alert style. Use the `redirectBack()` helper.
- **Namespace `personal`** is lowercase: `App\Models\personal\*`, `App\Http\Controllers\Personal\*` (controller namespace differs – PascalCase).
- **Settings** are stored in a `settings` DB table via `App\Models\Setting` (module, setting, value). Access centrally, not via `.env` for runtime config.
- **Permissions** are string-based: `'view wiki'`, `'edit vertretungen'`, `'create roster'`, `'has holidays'`, etc. New features must register permissions in their migration.

## Testing

```bash
php artisan test                 # Run all (PHPUnit, SQLite in-memory)
php artisan test --filter=Unit   # Unit tests only
```

- Tests use `RefreshDatabase` (see `TestCase.php`). Base `TestCase` calls `Http::preventStrayRequests()` – tests needing HTTP must call `Http::fake()` explicitly.
- Use `actingAsWithPermission('perm1', 'perm2')` from `TestCase` to create and authenticate a user with specific permissions.
- Use `Tests\Traits\CreatesTestData` for factories of complex domain objects (departments, rosters, diagnostic sessions, wochenplan).
- Factories exist in `database/factories/` for most models. Personal & Wochenplan factories are in subdirs.

## Common Patterns

- **New module checklist**: Model → Migration (with permission insert) → Controller → Form Request → Blade views → Route registration in `routes/web.php` (wrap with `permission:` middleware) → optional View Composer + dashboard card.
- **Observers** trigger notifications and recalculations. When adding model lifecycle hooks, add an Observer in `app/Observers/` and register it in `EventServiceProvider::boot()`.
- **Exports/Imports** follow Maatwebsite Excel patterns in `app/Exports/` and `app/Imports/`.
- **Scheduled tasks** are registered in `Console/Kernel.php` using `$schedule->call('Controller@method')` – not as separate commands.
