# AGENTS.md – MitarbeiterBoard

## Overview

Laravel 10 school intranet ("MitarbeiterBoard") for the Evangelisches Schulzentrum Radebeul. German-language domain (models, views, config). PHP 8.1+, MySQL/MariaDB, Vite + TailwindCSS v4, Alpine.js, Livewire 4, Bootstrap 4 (legacy).

## Architecture

- **Monolith** – single Laravel app, server-rendered Blade views, no SPA. Alpine.js handles interactive UI (diagnostics, wochenplan, sidebar).
- **Dual CSS** – Legacy pages use Bootstrap 4 (`public/css/`). Newer modules (diagnostics, paedDiary, wochenplan, rooms, sidebar) use Tailwind v4 via Vite. Tailwind preflight is **disabled** (`corePlugins.preflight: false`) to avoid Bootstrap conflicts. Tailwind is scoped via wrapper classes (e.g. `.diagnostic-wrapper`).
- **Vite entrypoints** are per-module, not a single bundle – see `vite.config.js`. Views load assets with `@vite()` and `@push('css')`/`@push('js')`.
- **Authorization** uses `spatie/laravel-permission` (RBAC). Permissions are checked via route middleware (`permission:view wiki`) and in controllers. Policies exist for `DiagnosticSession`, `DiagnosticArea`, `GradingDocumentationSession`, `Meeting`, Procedures, Personal and (API v1) `Schueler` (`StudentPolicy`) and `PaedDiaryEntry` (`PaedDiaryPolicy`).
- **SSO** via SAML2 (`aacotroneo/laravel-saml2`) and Keycloak (`socialiteproviders/keycloak`). Local auth can be toggled via `AUTH_LOCAL` env.
- **Meetings** can be group-bound (`group_id`) or free (`group_id = null`). Participants live in `meeting_participants` (polymorphic: `User` incl. `is_organizer`, `Group`, Spatie `Role`); visibility via `Meeting::scopeVisibleTo()` and `MeetingPolicy` (`view`/`contribute`/`manage`/`viewTheme`). Group-independent UI under `/meetings` (`app/Http/Controllers/Meetings/`), shared logic in `Services/Meetings/MeetingService`. Themes may be free (`themes.group_id = null`) and are then only reachable via `meetings/{meeting}/agenda/{theme}`. New agenda themes can be assigned to the meeting group or any invited group (`MeetingService::themeGroupOptions()`/`isValidThemeGroup()`), so unfinished themes stay in that group's list; free themes only in free meetings. Existing open agenda themes can be moved later via `meetings.themes.move` (`MeetingService::themeMoveTargets()`/`moveTheme()`; only themes whose current group belongs to the meeting). Global search: `Services/Search/GlobalSearchService` (includes themes/protocols of meetings the user participates in). Free meetings require the permission `create free meetings`. Invitations (`MeetingService::sendInvitations()`) can be limited to selected participants (`select_recipients` + `recipients[]`, validated in `validateInvitationRequest()`, UI `meetings/partials/invite_recipients.blade.php`); this only affects who gets the mail/push – access stays with all group members and invitees.
- **Theme tasks** (`Task`): personal (`taskable = User`) or collective (`taskable = Group|Meeting`, assignees in `group_task_users` with `completed_at` – rows are marked, never deleted, so "who completed" stays visible; unique per task+user). All creation/completion goes through `Services/Tasks/ThemeTaskService` (duplicate protection per person on same theme + same text). `Task` has a global scope hiding completed tasks – use `Task::withCompleted()` for history. Shared UI: `resources/views/tasks/partials/theme_tasks.blade.php` + `task_form.blade.php` (used by group and meeting theme pages).
- **Calendar (OX)**: OX (CalDAV) is the system of record; `ox_termine` is only a local cache filled by `OxCalendarService::syncAll()`. Every write goes to OX first. A termin can live in several calendars ("Terminverbund"): each copy is its own OX event (own UID), linked via `ox_termine.verbund_uid` and the iCal property `X-MB-VERBUND` (survives the OX roundtrip). Create/update/move/delete across copies only via `Services/Calendar/TerminVerbundService`; room bookings hang on the verbund (`room_bookings.ox_verbund_uid`) via `Services/Calendar/KalenderRaumService` (also renders room occupancy as FullCalendar events, incl. A/B weeks and VP cancellations). ICS import: `Services/Calendar/IcsImportService` + `CalendarImportController` (preview cached per user/token, permission `import calendar events`). Calendar CSS loads Tailwind utilities **unlayered** and resets Bootstrap element styles inside `.calendar-wrapper` – see header comment in `resources/css/calendar.css`.
- **Ticketsystem** (`Ticket`, `TicketComment`, `TicketCategory`): all creation, comments, status changes (open/waiting/closed, reopen), assignment, pins and notifications go through `Services/Tickets/TicketService`; access via `TicketPolicy` (`view`/`comment`/`manage`/`close`/`reopen`/`viewInternal` – creators see only their own tickets, `edit tickets` sees all and may comment internally). Mutating routes are POST. Rich-text (description/comments) is rendered only via `description_html`/`comment_html` (`App\Support\HtmlSanitizer`, HTMLPurifier). Attachments live on the private disk `tickets` and are served only via `tickets.files`. Waiting tickets are auto-closed daily (`closeExpiredWaiting`, settings `ticket_closed_automatic[_days]`). UI: Tailwind via `resources/css/tickets.css` + `resources/js/tickets.js`, scoped in `.ticket-wrapper` with `tkt-*` components; utilities are loaded **unlayered and `!important` with `source(none)`** (only ticket views are scanned) so they beat Bootstrap element styles – elements with display utilities need `x-show.important`. Below `lg`, list and detail are separate views.
- **Zeitwirtschaft** (Urlaub, Arbeitszeitnachweis, Dienstplan, Zeiterfassung): logic lives in `app/Services/Personal/Zeit/` – `ArbeitszeitService` (single source for Soll-Zeit/Arbeitstage from `Employment.percent` × Setting `vollzeit_stunden`, distributed over `employments.workdays`; public holidays computed locally in `App\Support\Feiertage`), `UrlaubskontoService` (Anspruch/Übertrag/Verfall/Rest, manual entries in `holiday_account_entries`), `HolidayService` (request/approve/reject/cancel + notifications), `TimesheetService` (Soll/Ist separation, balance cascade into following months, workflow offen → eingereicht → abgeschlossen), `RosterService` (create/copy weeks, absence markers `roster_events.source = 'abwesenheit'`, conflicts, publish + change log `roster_changes`, ICS feed), `TimeRecordingService` (Kommen/Gehen incl. § 4 ArbZG break). Access via `HolidayPolicy`/`TimesheetPolicy`/`RosterPolicy` and `ZeitZugriff` (superior chain incl. deputies from `user_deputies` – a deputy may do everything the represented leader may, if holding the permission; bulk maintenance under `personal/vorgesetzte`, `VorgesetzteController`; permissions `approve all holidays`, `manage all rosters`). Syncing is event driven: `HolidayObserver` and `AbsenceTimeObserver` keep absences (`absences.holiday_id`), timesheet credits (`timesheet_days.source` `urlaub`/`abwesenheit`, only on contract workdays) and roster markers consistent; `WorkingTimeObserver`/`RosterEventsObserver` log changes to published rosters. All mutating routes are POST/PUT/DELETE; `timesheets/{user}/{timesheet}` uses `scopeBindings()`. Terminal (`/time_recording`) keeps the scanned chip in the session only, PINs are hashed, throttled and lock after 5 failures; optional device binding via Setting `time_recording_terminal_token`. UI: Tailwind via `resources/css/zeit.css` + `resources/js/zeit.js` (Alpine `urlaubsAntrag`, `teamKalender`, `dienstplanEditor`), scoped in `.zeit-wrapper` with `zw-*` components, utilities unlayered/`!important` like tickets; roster editor loads its data via `roster.data` (JSON). Legacy protection: Setting `zeitwirtschaft_stichtag` – timesheets before it are calculated with the old method (`TimesheetService::berechneBisher()`), past ones are frozen (only recalculated on explicit edit/"Neu berechnen"); the old daily Soll uses the contracts valid on that day (`ArbeitszeitService::vertraegeAm()`), not their current status – expired contracts are set to `beendet` daily; the holiday balance continues from the stored `holidays_rest` of the month before the cutover (`UrlaubskontoService::basis()`). Check real data read-only with `php artisan personal:zeit-umstellung-pruefen`. Tests: `tests/Feature/Personal/Zeit/`.
- **Guided tours** (`<x-tour>`, `resources/views/components/tour.blade.php` + Vite entry `resources/js/tour.js`/`resources/css/tour.css`) are reusable in every module: mark elements with `data-tour="name"`, define steps in Blade (`target`/`selector`, optional `activate` to click a tab first, `title`, `text`; `null` steps are dropped, steps with missing/hidden targets are skipped), add a start button with `data-tour-start="<id>"`. Auto-starts once per user/browser/`version` (localStorage), `?tour=<id>` forces a start, `next` chains to the next page. The component pushes its own assets. Plain CSS (`mbt-*`) because the overlay lives outside the module wrappers; don't use the `hidden` attribute for styling (Bootstrap forces `display:none !important`). Current chain: Eigene Daten → Mein Profil → Urlaub → Arbeitszeitnachweis (`tests/Feature/Personal/EinfuehrungsTourTest.php`).
- **Online updater** (`/updater`, permission `make updates`): `UpdateController` starts `php artisan app:update` detached (`nohup`) via `Services/Updater/UpdaterService`; the command mirrors `deploy.sh` (fetch → preflight → `down` → `git merge --ff-only` → composer → `npm run build` only if frontend files changed → `migrate --force`/cache clears/`queue:restart` as subprocesses → `up`). Status, log and `flock` lock live in `storage/app/updater/`; the UI polls `updater/status` (both updater URIs are in `PreventRequestsDuringMaintenance::$except`). If composer/npm fail the code is reset to the previous commit; once migrations started there is no automatic rollback. Config: `config/updater.php` (`UPDATER_*` env). UI: Tailwind via `resources/css/updater.css` + `resources/js/updater.js` (Alpine `updater`: polling, phase stepper, confirm dialog), scoped in `.upd-wrapper` with `upd-*` components, utilities unlayered/`!important` like tickets. Tests: `tests/Feature/Updater/` (temporary git repos).
- **Dashboard** is card-based, powered by View Composers (`app/View/Composers/`) registered in `ViewServiceProvider`. Each card is a Blade partial.

- **REST API v1** (Pädagogen-App) under `/api/v1`, Laravel Sanctum bearer tokens (`auth:sanctum` + `permission:view paed diary`). Controllers in `app/Http/Controllers/API/v1/`, Form Requests in `app/Http/Requests/API/v1/`, Resources in `app/Http/Resources/API/v1/`, shared queries in `app/Services/Api/StudentDataService.php`. Spec: `resources/api-docs/openapi-v1.yaml`, tests: `tests/Feature/API/v1/`. Keep the OpenAPI file in sync when changing endpoints.
  - Teacher routes use `auth:sanctum`, `api.staff` (rejects student tokens, extends token lifetime), `permission:view paed diary` and `idempotent` (optional `Idempotency-Key`; runs before route-model binding via `Kernel::$middlewarePriority`). Student-iPad routes (`/api/v1/student/*`) use `auth:sanctum` + `api.student`; their tokens belong to `GradingStudentDevice`, never to a `User`.
  - Shared logic for web and API: `GradingSessionService` (grading sessions), `GradingStageService` (stage changes), `Api\DossierService` (dossier JSON/PDF, view `pdf/dossier.blade.php`), `PaedDiaryCalendarService` (week view), `PaedDiaryTaskService` (tasks), `PaedDiaryAppointmentService` (appointments).
  - Roster API (`/api/v1/roster/*`, `RosterApiController`): own group with `auth:sanctum` + `api.staff` + `idempotent` but **without** `permission:view paed diary`; planning routes need `permission:create roster` + `RosterPolicy`. All logic (incl. `raster()`, `arbeitszeitSetzen()`, `termineAnlegen()`, `kollision()`, calendar import `kalenderImportVorschau()`/`kalenderImportieren()` – dedup per OX event + day) lives in `RosterService` and is shared with the web editor. The plan detail additionally returns (for planners) `previous_id`/`next_id`, `event_names`, `notes` (RosterNews) and `changes`; extra endpoints mirror the web editor: clear day (`DELETE rosters/{id}/days/{date}`, keeps absences) and notes (`POST rosters/{id}/notes`, `DELETE notes/{id}`). Tests: `tests/Feature/API/v1/RosterApiTest.php`.
  - Dienstplan-App (Flutter, separates Repo `dienstplan_app`): logs in with `app=dienstplan` on `auth/token` / `auth/sso/exchange` (redirect `dienstplan://auth`). Access per app via `ApiTokenService::hasAppAccess($user, $app)` – `paed` needs `view paed diary`, `dienstplan` needs `create roster` or membership in a group with `needsRoster`. `auth/me`, `auth/token` (DELETE) and `auth/devices*` only require `auth:sanctum` + `api.staff`; `EnsureIdempotency` uses `hasAnyAppAccess()`.
  - Timesheet API (`/api/v1/timesheets/*`, `TimesheetApiController`): group with `auth:sanctum` + `api.staff` + `idempotent`, **without** `view paed diary`. Access strictly via `TimesheetPolicy`/`ZeitZugriff` per person (`viewEmploye`) or per timesheet (`view`/`edit`/`submit`/`lock`/`returnToEmploye`/`unlock`) – own timesheets, subordinates for superiors/deputies with `lock timesheets`, all with `edit employe`. Write routes address the timesheet/day by ID only (no user in the path), so there is nothing to cross-bind. All logic (incl. `fuerAnzeigeAktualisieren()`, `pdf()`, `fehlendesGehen*()`) lives in `TimesheetService` and is shared with the web `TimesheetController`. `months/{month}` creates/updates open timesheets (incl. automatic roster import) – for side-effect-free reads use `GET timesheets/{id}`; explicit recalculation via `POST {id}/recalculate` (with following months) and `POST employees/{id}/recalculate` (all open months, like the web). Own check-in/out: `GET/POST timesheets/clock` (`has timesheet`, `action` in|out, explicit instead of toggling – 422 if already in/out) via `TimeRecordingService::stempeln()`; used by the app's opt-in location reminder (geofence stays on the device). Tests: `tests/Feature/API/v1/TimesheetApiTest.php`.
  - Holiday API (`/api/v1/holidays/*`, `HolidayApiController`, group with `permission:has holidays|approve holidays`) and Absence API (`/api/v1/absences/*`, `AbsenceApiController`, `permission:view absences`), both `auth:sanctum` + `api.staff` + `idempotent`, used by the Dienstplan-App tab „Zeit“. Holiday rights via `HolidayPolicy`; `antragsNutzer()`/`zuEntscheiden()` live in `HolidayService` (shared with the web `HolidayController`). Absence create/delete goes through `Services/AbsenceService` (shared with the web `AbsenceController`: self-only without `create absences`, extending an adjacent absence with the same reason, notification). Absences from holidays (`holiday_id`) can't be deleted via the API. The Dienstplan app is also open to users with `has timesheet`, `lock timesheets`, `has holidays`, `approve holidays` or `view absences`; `auth/me` reports `timesheets`/`holidays`/`approve_holidays`/`absences`/`create_absences`. Tests: `tests/Feature/API/v1/HolidayApiTest.php`, `AbsenceApiTest.php`.
  - Application tokens ("Anwendungstokens"): users with `create api tokens` create their own Sanctum tokens under Mein Profil (tab „Pädagogen-App & API“) and Eigene Daten (`resources/views/personal/_api_tokens.blade.php`, `ApiTokenController`, route `self-service.api-tokens.store`; revoke via `self-service.app-devices.destroy`). They carry the ability `api-token` (`ApiTokenService::API_TOKEN_ABILITY`), have a fixed lifetime (no sliding extension in `EnsureStaffToken`) and are excluded from the app device list (`ApiTokenService::tokensFor()`). The plain token is shown once via session flash. Tests: `tests/Feature/API/v1/ApiTokenProfileTest.php`.
  - Diary content is encrypted at rest (`PaedDiaryEntry::setContentAttribute`), so full-text search cannot use SQL – `Api\PaedDiarySearchService` decrypts pre-filtered entries and matches in PHP (max. 5000 per search). App config: `config/paed_app.php`.

## Conventions

- **Language**: All UI text, model names, comments, and config keys are in **German** (e.g. `Schueler`, `Klasse`, `Vertretung`, `Wochenplan`, `Meldung`). Keep this convention.
- **Flash messages** use `session('Meldung')` with `session('type')` for alert style. Use the `redirectBack()` helper.
- **Namespace `personal`** is lowercase: `App\Models\personal\*`, `App\Http\Controllers\Personal\*` (controller namespace differs – PascalCase).
- **Settings** are stored in a `settings` DB table via `App\Models\Setting` (module, setting, value). Access centrally, not via `.env` for runtime config.
- **Permissions** are string-based: `'view wiki'`, `'edit vertretungen'`, `'create roster'`, `'has holidays'`, etc. New features must register permissions in their migration.

## Testing

```bash
php artisan test                 # Run all (PHPUnit, SQLite in-memory)
php artisan test --filter=Unit   # Unit tests only
```

- Tests use `RefreshDatabase` (see `TestCase.php`). Base `TestCase` calls `Http::preventStrayRequests()` – tests needing HTTP must call `Http::fake()` explicitly.
- Use `actingAsWithPermission('perm1', 'perm2')` from `TestCase` to create and authenticate a user with specific permissions.
- Use `Tests\Traits\CreatesTestData` for factories of complex domain objects (departments, rosters, diagnostic sessions, wochenplan).
- Factories exist in `database/factories/` for most models. Personal & Wochenplan factories are in subdirs.

## Build & Deploy

```bash
npm run build          # Vite production build (npm run build:vite)
npm run dev:vite       # Vite dev server with HMR
composer install       # PHP dependencies
php artisan migrate    # DB migrations
```

- **Deploy**: `./deploy.sh` (git pull → composer install → migrate → cache:clear).
- **Scheduler**: Runs mail reminders, ticket auto-close, recurring theme creation, timesheet mails – see `app/Console/Kernel.php`.
- **Queue**: Required for mail/notifications: `php artisan queue:work`.

## Common Patterns

- **New module checklist**: Model → Migration (with permission insert) → Controller → Form Request → Blade views → Route registration in `routes/web.php` (wrap with `permission:` middleware) → optional View Composer + dashboard card.
- **Observers** trigger notifications and recalculations. When adding model lifecycle hooks, add an Observer in `app/Observers/` and register it in `EventServiceProvider::boot()`.
- **Exports/Imports** follow Maatwebsite Excel patterns in `app/Exports/` and `app/Imports/`.
- **Scheduled tasks** are registered in `Console/Kernel.php` using `$schedule->call('Controller@method')` – not as separate commands.
